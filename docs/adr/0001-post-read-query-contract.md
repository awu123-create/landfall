# 0001. 作品读接口与多维检索契约

- **状态**：Proposed（提案中）
- **日期**：2026-11-26
- **关联**：Issue #23（本 ADR 与读接口契约正文）、#22（父切片）、#24、#25
- **影响工作包**：包 3（主）、包 2（表结构与写链路）、包 4（互动状态）、包 7（推荐排序）

## 背景

包 3 负责「浏览与检索」：发现流、作品详情、多维检索与我的作品。当前仓库只有 `common` 公共契约底座，这四组读接口尚无书面契约。而它们同时是其他工作包的依赖面——包 2 要据此建表与索引，包 7 要提供推荐排序，包 4/包 5 要往详情页挂互动与关注组件。若不先固化，各包会按各自假设开工。

本 ADR 记录**决策与取舍**；接口的字段级契约登记在 [docs/standards/api-contract.md](../standards/api-contract.md) 的「作品读接口」小节，二者不重复描述同一内容。

## 决策

### D1. 作品详情采用独立页 `/posts/{postId}`

详情页是全组唯一的内容聚合入口。选择独立路由而非卡片上浮弹窗，理由：

- URL 可直接分享与刷新还原，评审与答辩时可直接复制链接；
- 包 4/包 5/包 7 的特性组件有稳定的挂载容器，不必为弹窗另设一套生命周期；
- 路由级懒加载天然成立。

放弃弹窗形态的代价是浏览连贯性下降，由列表返回时的滚动位置恢复弥补（在页面壳切片验证）。

### D2. 发现流只做 `page` + `pageSize`，不实现 `cursor`

`cursor` 解决的是「新帖插入导致翻页重复/删帖导致漏条」。本项目答辩数据规模为数百条、演示期间无并发写入，该问题不成立。`PageResult` 已预留可选 `cursor` 字段，日后需要时是增量改动。

### D3. 首页默认排序档位为 `LATEST`，`RECOMMEND` 未就绪时降级

`RECOMMEND` 依赖包 7 的排序服务。若把它设为默认，包 7 合入前首页将无内容。故默认 `LATEST`（自足、永远可用），`RECOMMEND` 在排序服务缺失时返回与 `LATEST` 等价的结果并在响应中标注降级标记，前端可据此提示。

### D4. 关键词检索使用 `ILIKE`，不引入 `pg_trgm`

仓库已明确弃用 `pg_trgm`：其对 1~2 字中文词失效，而中文社区的高频检索词恰恰是短词。代价是 `ILIKE '%关键词%'` 无法使用 B-tree 索引，等价于全表扫描。

**接受该代价的前提**：当前数据规模（数百条）下单次扫描为毫秒级。**重新评估阈值**：`posts` 表行数超过 1 万，或单次检索 P95 超过 200ms。届时可选方向为恢复 `pg_trgm`、引入中文分词扩展，或改用独立检索组件——三者都超出当前课程范围。

### D5. 检索使用独立端点，不与发现流复用

`GET /api/v1/public/posts/search` 与 `GET /api/v1/public/posts` 分开：

- 语义不同：发现流是「按热度/时间看内容」，检索是「给定条件找内容」，后者要求至少一个筛选条件成立，禁止无参调用避免全表导出；
- 非功能策略不同：检索的限流、缓存键与排序实现都不同于发现流；
- 合并成一个端点会让它逐步演化成万能接口，后续无法判断调用意图。

### D6. 「不存在」与「无权查看」返回同一响应

详情接口对 `PRIVATE` 作品、他人 `FRIENDS` 作品、`TAKEDOWN` 作品与真正不存在的 ID，统一返回 `404` + `30001`。若区分，攻击者可借响应差异探测某篇作品是否存在。

### D7. 与包 2 在 `module.post` 内的文件级边界

包 2 与包 3 都改 `module.post`，因此约定：包 2 独占写链路（创建/编辑/删除、媒体绑定、标签写入）与 `PostAccessPolicy` 实现；包 3 只拥有公开查询入口与只读查询实现，且**只调用** `PostAccessPolicy` 而不修改其判定逻辑。改动落在同一文件时，先在 Issue #22 下留言对齐。

## 后果

- 包 2 建表时可直接按 [api-contract.md](../standards/api-contract.md) 的字段与 `docs/standards/database.md` 的索引约定设计 `posts` / `post_tags` / `media_assets` 结构，无需等待包 3 的实现代码。
- 包 4 的批量互动状态查询（#21）合入后，详情聚合的 `currentUser` 字段才能填充真实值；在此之前按契约返回 `null`。
- 检索的排序稳定性需要显式 tie-breaker（`created_at DESC, post_id DESC`），否则同秒创建的作品在翻页时可能重复——这一点在实现切片中必须有测试覆盖。
